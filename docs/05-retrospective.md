# 回顾与反思

## 最难的问题

### next_action 的回填时机

执行当前步骤时尚不知道模型下一步会做什么，无法在创建 StepRecord 时就填写 `next_action`。解决方案是引入 `prev_rec` 变量，在每轮新决策产生后回填到上一步记录。这个"延迟写入"的思路在实时系统中很常见，但初次实现时容易遗漏边界情况（循环退出时的最后一步、上限中断时的回填）。

### 工具失败后的恢复决策

Mock 模型只能看到最近一条工具返回（`_last_tool`），要实现失败恢复需要回溯更早的消息历史。设计了 `_find_search_results()` 从全量 messages 中提取素材检索结果，配合 `state.failed_steps` 追踪已尝试过的素材 ID，避免死循环重试。这体现了 ReAct 中"观察"不仅是当前结果，也包含历史上下文。

## 学习收获

1. **ReAct 模式的本质**：不是"调用工具的固定流程"，而是"模型根据观察结果动态调整下一步"。关键区分在于：相同的输入在不同工具返回下会产生不同的执行路径
2. **状态分离的重要性**：将 completed_steps 和 failed_steps 分开存储，既满足了"失败不记成功"的要求，又为失败恢复提供了已尝试记录的查询基础
3. **幂等设计**：用 SHA256 哈希生成幂等键，保证同一请求多次执行的一致性，这在生产系统中是必备能力
4. **Mock 与真实模型的边界**：Mock 能验证流程正确性但无法证明模型决策质量。关键是保持 decide 接口的返回结构一致，使切换模型时循环逻辑零改动

## 下一步改进


1. **接入真实 LLM**：当前 `_decide_real()` 已实现 OpenAI 兼容接口，配置 API Key 即可切换，验证真实模型在相同场景下的决策质量
2. **更多失败恢复策略**：目前仅 generate_script 有续跑逻辑，search_material 和 save_plan 失败时可增加重试或降级方案
3. **case_buget_over 差异化**：当前与 case_normal 走相同路径，应设计一个所有方案均超预算的用例，验证"返回 incomplete 及缺口"的场景
4. **维护 selected_plan**：在 agent.py 或 mock_llm 中正确更新 AgentState.selected_plan，支持多轮方案切换
5. **增加并行工具调用**：多个独立工具可并行执行，减少总耗时
